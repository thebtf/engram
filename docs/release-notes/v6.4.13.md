# v6.4.13

## Fixed

### Claude Code plugin MCP server silently not spawning

The plugin `.mcp.json` declared an `env` block that interpolated
`${user_config.server_url}` and `${user_config.api_token}`. Claude Code has a
known defect (anthropics/claude-code#51573) where `${user_config.*}`
references inside a plugin `mcpServers` `env` block cause the MCP server to be
silently skipped at session start: the server never appears in `/mcp` or
`claude mcp list`, and no error is surfaced. Hooks from the same plugin keep
running, so the plugin looks half-alive — session-start context is injected
while every `mcp__plugin_engram_engram__*` tool is missing.

The fix removes the `env` block from `.mcp.json` entirely. Credential
resolution now uses the documented plugin-subprocess environment contract:

1. `ENGRAM_URL` / `ENGRAM_TOKEN` from the host environment
   (`~/.claude/settings.json` `env` for Claude Code,
   `[shell_environment_policy.set]` in `~/.codex/config.toml` for Codex) —
   highest precedence, unchanged.
2. `CLAUDE_PLUGIN_OPTION_server_url` / `CLAUDE_PLUGIN_OPTION_api_token` —
   Claude Code exports every plugin `userConfig` value to plugin subprocesses
   under `CLAUDE_PLUGIN_OPTION_<KEY>`. The wrapper, session-start hook, and
   hook HTTP client now read these as fallbacks, so filling in the plugin's
   userConfig prompts is sufficient on a fresh workstation.
3. Legacy `ENGRAM_CLAUDE_USERCONFIG_*` names remain accepted for
   compatibility with externally-pinned configs.

A regression test asserts `.mcp.json` never reintroduces `${user_config.*}`
in an `env` block.

## Upgrade notes

Update/reinstall the plugin from the marketplace. No server-side change. If
`ENGRAM_URL`/`ENGRAM_TOKEN` are already configured in your agent host
environment, no action is needed — that path is unchanged and still wins.
