# DESIGN-SYNC PROTOCOL — двусторонняя синхронизация дизайна и кода

Протокол синхронизации между разработчиком и дизайн-агентом. **Два канала, оба
обязательны:**

- **Канал A — заказ (dev → дизайн).** Разработчик: «спроектируй раздел X» → получает
  дизайн в предсказуемом формате → встраивает в код быстро, без переразметки и без
  потери того, что спроектировано. (Разделы 1–6.)
- **Канал B — заявка на переделку (дизайн → dev).** Дизайнер: «здесь плохой UX, функцию
  надо переделать так, чтобы в дашборде работало вот так» → разработчик **принимает в
  работу и подтверждает**. Находка не повисает: у неё есть статус, владелец и приёмка.
  (Разделы 7–9.)

Канал B — не «жалоба», а полноценный change request с тем же уровнем строгости, что и
заказ: воспроизводимая проблема, конкретное предложение, ожидаемое поведение и явное
подтверждение разработчика, что он берёт это в работу.

Документ двуязычный по необходимости: заголовки/обсуждение — для человека (RU),
контракт и шаблоны — машинно-стабильные (структура, имена классов, токены).

---

## 0. Зачем протокол (одна мысль)

Дизайн-агент выдаёт **самодостаточный HTML-прототип в общих токенах**. Разработчик
НЕ переписывает его — он **подменяет источник данных за готовыми швами** и переносит
компоненты в свой фреймворк по карте классов. Контракт ниже делает этот перенос
механическим.

Три уже существующих документа — фундамент, на который опирается этот протокол:
- `components.html` — живая галерея переиспользуемых компонентов (что есть).
- `DEVELOPER-PLAYBOOK.md` — как вшить auth/данные за швами (как переносить).
- `ACCESS-ADMIN-spec.md` — пример спеки раздела (структура сущностей).

---

## 1. Формат ЗАКАЗА (что присылает разработчик)

Разработчик открывает заказ одним блоком. Чем полнее — тем меньше итераций. Минимум:

```
ЗАКАЗ РАЗДЕЛА
name:        <slug-раздела>            # напр. webhooks, api-keys, billing
audience:    <кто пользователь>        # оператор / админ воркспейса / суперадмин
surface:     <self-hosted | saas | both>
placement:   <где живёт>               # напр. "Settings → группа Доступ" / "отдельная консоль"
entities:    <список сущностей>        # напр. webhook{url,events[],secret,status}, delivery{...}
actions:     <глаголы>                 # создать/изменить/удалить/тест/отозвать/...
states:      <состояния и пустые>      # loading / empty / error / disabled-by-flag
constraints: <правила>                 # секреты write-only, read-only прод, гейт за флагом X
reuse:       <что обязательно переиспользовать>   # Entity Row, settingRow, .toggle, PROVIDER_MARK
nonzero:     <чего НЕ делать>          # не плодить второй акцент, не трогать топбар
```

Если поля не заданы — агент берёт дефолты из дизайн-системы и **называет принятые
решения** в ответе (не молчит).

---

## 2. Что ВОЗВРАЩАЕТ дизайн-агент (контракт поставки)

На каждый заказ — три обязательных артефакта, всегда одинаково названных:

1. **`section-<name>.html`** — самодостаточный кликабельный прототип раздела в общих
   токенах (тёмная тема по умолчанию). Это «витрина для обсуждения».
2. **`section-<name>.handoff.md`** — карта вшивки (см. §3). Это «инструкция для кода».
3. **(если раздел сложный)** запись в `ACCESS-ADMIN-spec.md`-стиле — структура
   сущностей, чтобы не потерять между сессиями.

Прототип ВСЕГДА:
- использует только токены `:root` из дизайн-системы (никакого raw hex);
- переиспользует компоненты из `components.html` по их классам;
- маркирует honesty-классификацию (`live / gate / mb / status`), если есть мёртвые/
  флаг-гейтнутые элементы;
- держит секреты `type=password`, мутации — за явным действием.

---

## 3. Карта вшивки — `section-<name>.handoff.md` (ядро протокола)

Это то, что превращает «красивый HTML» в «быстро встроить». Жёсткий шаблон:

```markdown
# Handoff: <name>

## A. Точка монтирования
- Куда вставляется: <файл/функция/роут>            # напр. index.html → SETTINGS_TABS + dispatch
- Механизм: <как именно>                            # напр. "добавить tab в группу, ветка в renderSettingsModalBody"
- Зависимости: <что должно существовать>            # PROVIDER_MARK, openPopoverAt, confirmModal

## B. Данные (швы mock → live)
| Mock-константа | Форма (поля) | Реальный источник | Адаптер |
|---|---|---|---|
| SECTION_ITEMS | {id,name,status,...} | GET /api/<name> | map x→{...} |
- Правило: СОХРАНИ форму, поменяй источник (как в DEVELOPER-PLAYBOOK §2).

## C. Действия (швы кнопок → API)
| Кнопка/событие | Эффект в прототипе | Реальный вызов |
|---|---|---|
| «Создать»      | unshift в массив   | POST /api/<name> |
| «Удалить»      | confirmModal+filter| DELETE /api/<name>/:id |

## D. Компоненты (карта классов → твой фреймворк)
| Класс прототипа | Что это | React/Vue-эквивалент |
|---|---|---|
| .erow / .ac-tbl | строка/таблица | <EntityRow> / <DataTable> |
| settingRow(...)  | строка настройки | <SettingRow label desc>{control} |
| .toggle[aria-checked] | переключатель | <Toggle checked> |

## E. Состояния
- loading: <как показать>      # пустой массив → empty-row, не спиннер поверх
- empty:   <текст/композиция>
- error:   <как падает>        # 401 → showAuthGate(); прочее → callout danger
- gated:   <если за флагом>    # бейдж gate + причина

## F. Инварианты (НЕ потерять)
- [ ] секреты write-only
- [ ] единый акцент, tabular-nums на числах
- [ ] honesty-бейджи отражают реальное состояние
- [ ] mustbuild-пилюли сняты только когда есть бэкенд
```

Разработчик читает A→F сверху вниз и за один проход знает: куда вставить, что
подменить, чем заменить компоненты, как обработать состояния, что нельзя сломать.

---

## 4. Два режима вшивки (выбирает разработчик)

**Режим 1 — «как есть» (vanilla / встраиваемый виджет).** Раздел переносится в
проект почти дословно: прототип уже на токенах и ванильном JS. Подменяются массивы-
константы на `fetch` за швами §3.B/§3.C. Это путь `index.html` (мы так и встроили
группу «Доступ»). Самый быстрый.

**Режим 2 — «шаблонизация» (React/Vue/Svelte).** Прототип — визуальный эталон;
разработчик собирает компоненты своего фреймворка по карте §3.D, копируя разметку
блоков в JSX/template и заменяя инлайн-обработчики на хендлеры. Токены переносятся
один раз как CSS-переменные (`tokens.css`). Дольше, но даёт «настоящие» компоненты.

Протокол одинаков для обоих; меняется только §3.D (карта на конкретный фреймворк).

## 5. Контрольный список приёмки (Definition of Done одного раздела)

- [ ] `section-<name>.html` открывается, кликается, переключает тему.
- [ ] `section-<name>.handoff.md` заполнен A→F без пропусков (нет `NO DATA` в
      обязательных швах, либо причина названа).
- [ ] Каждый компонент взят из `components.html` или добавлен туда как новый.
- [ ] Новые классы под своим префиксом (напр. `.wh-*` для webhooks), не ломают
      глобальные.
- [ ] Node-парсинг встроенного скрипта проходит; теги сбалансированы.
- [ ] Honesty-классификация и write-only секреты на месте.
- [ ] Иконки уникальны по смыслу (нет дубля метафоры с существующими).

## 6. Пример заказа (end-to-end, для калибровки)

```
ЗАКАЗ: name=webhooks, audience=админ воркспейса, surface=saas,
placement="настройки воркспейса → Интеграции", entities=webhook{url,events[],secret,status},
actions=создать/тест/отключить/удалить, constraints=secret write-only,
reuse=.ac-tbl,settingRow,.toggle, nonzero=не трогать топбар.
```
Ответ агента: `section-webhooks.html` + `section-webhooks.handoff.md` (A: вставка в
SaaS-консоль → роут integrations; B: WEBHOOKS→GET /api/workspaces/:id/webhooks; C:
test→POST .../test; D: .ac-tbl→<DataTable>; E: empty="Пока нет вебхуков"; F: secret
скрыт). Разработчик за один проход вшивает.

# КАНАЛ B — заявка на переделку (дизайн → dev)

Обратное направление. Дизайнер видит, что функция в дашборде работает плохо, и
**инициирует** изменение: формулирует проблему и предлагает, как должно быть. Это не
повисает как мнение — у заявки есть формат, статус и обязательная приёмка
разработчиком.

## 7. Формат ЗАЯВКИ НА ПЕРЕДЕЛКУ (что присылает дизайнер)

Дизайнер открывает заявку одним блоком. Симметрично заказу, но инициатор — дизайн.

```
ЗАЯВКА НА ПЕРЕДЕЛКУ (UX-CR)
id:          UX-<NNN>                  # сквозной номер
target:      <раздел / экран / компонент>     # напр. "Settings → Доступ → Пользователи"
severity:    blocker | major | minor   # blocker = функция реально не выполнима в UI
problem:     <что плохо, наблюдаемо>    # «массовая смена роли невозможна: только построчно»
evidence:    <как воспроизвести>        # шаги / скрин с пометкой / ссылка на экран
impact:      <кого и как бьёт>          # «админ на 50 юзеров кликает 50 раз»
proposal:    <как должно работать>      # «чекбоксы строк + bulk-bar → сменить роль выбранным»
behaviour:   <ожидаемое поведение>      # точное: что появляется, что меняется, что сохраняется
backend_ask: <что нужно от функции>     # «PATCH /users/bulk {ids[],role} — иначе чисто UI-фейк»
reuse:       <чем закрывается>          # «существующий .bulkbar + selected Set, как в Memory Lab»
scope_guard: <чего НЕ трогаем>          # «роутинг и данные не меняем, только массовое действие»
```

Ключевое отличие от баг-репорта: **есть `proposal` + `behaviour` + `backend_ask`** —
дизайнер не только жалуется, а приносит решение и честно отмечает, требует ли оно
изменения функции на бэкенде (а не только перерисовки).

## 8. Цикл приёмки (статусы — заявка не висит)

Заявка проходит фиксированный жизненный цикл. Статус всегда явный:

```
open ──→ acknowledged ──→ accepted ──→ in-progress ──→ done ──→ verified
  │             │              │
  └─ declined   └─ needs-info  └─ deferred(<когда/почему>)
```

- **open** — дизайнер создал.
- **acknowledged** — разработчик прочитал и понял (не молча). Здесь же `needs-info`,
  если `evidence`/`behaviour` недостаточны — пинг обратно дизайнеру.
- **accepted** — разработчик **подтверждает, что берёт в работу**. Это обязательная
  точка: без явного accepted заявка не считается принятой. Разработчик пишет короткий
  `dev_ack` (см. §9) — чем закрывает, какой бэкенд-шов добавляет.
- **declined** — отказ ТОЛЬКО с причиной (технический предел / противоречит инварианту /
  дешевле иначе) и контрпредложением, если есть. Дизайнер может оспорить.
- **deferred** — согласны, но не сейчас; обязательно «когда/при каком условии».
- **in-progress → done** — сделано в коде.
- **verified** — дизайнер подтвердил, что переделанное поведение соответствует
  `behaviour` из заявки. Цикл закрывается тем, кто его открыл (симметрия с приёмкой
  заказа).

Правило против застоя: заявка в `open` без `acknowledged` — это незакрытый долг
разработчика, ровно как заказ без поставки — долг дизайнера. Обе стороны обязаны
двигать статус, а не игнорировать.

## 9. Подтверждение разработчика — `dev_ack` (обязательное на `accepted`)

Чтобы «принял в работу» было не на словах, разработчик на переходе в `accepted`
заполняет короткий ответ — симметрию handoff'а, но со своей стороны:

```markdown
## dev_ack для UX-<NNN>
- status: accepted
- принимаю поведение: <да / с оговоркой: ...>      # совпадает ли с proposal.behaviour
- бэкенд-шов: <что добавляю>                        # напр. "PATCH /users/bulk — новый эндпойнт"
   - или: backend не нужен, чисто UI                # если переделка только клиентская
- точка в коде: <файл/функция>                      # куда ляжет (как §3.A заказа)
- инварианты сохранены: <да + какие>                # write-only секреты / единый акцент / honesty
- оценка: <S / M / L>                               # грубо, для очереди
- когда: <в этом проходе / следующий CR / deferred> 
```

`dev_ack` закрывает контур: дизайнер видит не «ок, посмотрю», а конкретное
обязательство — какое поведение принято, каким бэкенд-швом, где в коде, что не сломано.
Если `proposal` требовал `backend_ask`, а `dev_ack` говорит «чисто UI» — это сигнал
рассинхрона: переделка будет выглядеть работающей, но останется фейком (нарушение
honesty-контракта). Такой случай возвращается в `needs-info`.

## 9a. Пример заявки (end-to-end, для калибровки)

```
UX-014  target="Settings → Доступ → Пользователи"  severity=major
problem: массовая смена роли невозможна — действия только построчно.
evidence: 50 пользователей → 50 отдельных кликов «Роль».
impact: админ воркспейса тратит минуты на рутину, ошибается.
proposal: чекбоксы строк + sticky bulk-bar «Выбрано N → Сменить роль / Отключить».
behaviour: выбор строк копит Set; bulk-bar показывает счётчик; «Сменить роль» открывает
  тот же role-меню, применяет ко всем выбранным; toast с откатом.
backend_ask: PATCH /api/users/bulk {ids[],role} — иначе массовость будет UI-фейком.
reuse: .bulkbar + selected Set + updateBulk() — уже есть в Memory Lab.
scope_guard: данные/роутинг не трогаем, только массовое действие в таблице.
```
Ответ разработчика (`dev_ack`, accepted): принимаю поведение — да; бэкенд-шов — новый
`PATCH /users/bulk`; точка — `renderAccessUsers` + общий `.bulkbar`; инварианты — да
(honesty: пока эндпойнта нет, кнопка с пилюлей «нужен backend»); оценка M; когда —
следующий CR. → дизайнер позже переводит в `verified`.

## 10. Где лежат опорные документы

- `components.html` — галерея компонентов (открыть в браузере).
- `DEVELOPER-PLAYBOOK.md` — швы данных/auth, порядок миграции mock→live.
- `ACCESS-ADMIN-spec.md` — образец спеки сущностей раздела.
- `DESIGN.md` / `:root` в `index.html` — токены (источник правды по цвету/типу).
- `access-admin.html`, `saas-admin.html` — эталонные макеты двух поверхностей.

## Сводка двух каналов

| | Канал A (заказ) | Канал B (переделка) |
|---|---|---|
| Инициатор | разработчик | дизайнер |
| Вход | `ЗАКАЗ РАЗДЕЛА` (§1) | `ЗАЯВКА НА ПЕРЕДЕЛКУ` (§7) |
| Поставка | `section-*.html` + `handoff.md` (§2–3) | прототип переделки + правка в коде |
| Приёмка | разработчик вшивает, дизайнер сверяет витрину | разработчик `dev_ack` accepted (§9), дизайнер `verified` |
| Антизастой | заказ без поставки — долг дизайнера | заявка без `acknowledged` — долг разработчика |

Оба канала используют один контракт компонентов, одни токены, один honesty-инвариант.
Разница только в том, кто инициирует и кто подтверждает закрытие.

## 11. Канал C — синхронизация дрейфа (макет ↔ порт во фреймворке)

Каналы A и B — про **отдельные разделы** (заказать / переделать). Канал C — про
**непрерывное расхождение** между макетом-контрактом (`.od/*.html`) и портом в реальном
фреймворке (`nuxt-port/`). Это не разовое событие, а постоянное состояние, за которым
нужен учёт.

### Принцип (одна мысль)

**Кодогенерации макет→Vue нет и не будет.** Макет — vanilla JS/HTML, порт — Vue SFC +
Nuxt UI; автоперевод хрупок и плодит два источника правды, которые гниют. Вместо
автоматизации — **реестр дрейфа**: разработчик *следует* за макетом по карте классов
(§3 D, `DEVELOPER-PLAYBOOK §8a`) и готовым компонентам, а реестр делает это «следование»
проверяемым, а не доверительным.

### Механизм (три артефакта)

1. **Штамп контракта** — `design_version` в шапке `DESIGN.md`. Бампается при любом
   изменении токена / компонента / экрана.
2. **Реестр** — `nuxt-port/PARITY.json`: по строке на раздел (секция макета → страница
   порта → уровень фиделити → статус синхронизации → к какой версии синхронизирован →
   именованные пробелы). Человекочитаемая обвязка — `nuxt-port/PARITY.md`.
3. **Детектор** — `npm run parity` (`scripts/parity-check.mjs`, без зависимостей).
   Падает, когда штампы разошлись, раздел помечен `drifted`, `synced_to` отстал, или
   страница пропала/без строки. Ставится в CI, чтобы дрейф был громким, а не молчаливым.

### Рутина

- **Дизайнер меняет раздел** → бампает `design_version` → ставит затронутым строкам
  `sync: "drifted"` (найти затронутые помогает поле `components` в каждой строке: правка
  поведения компонента флагует ровно те разделы, что его используют).
- **`npm run parity` краснеет** → разработчик делает catch-up → возвращает строки в
  `synced`, обновляет `synced_to`, подрезает закрытые `gaps`.
- **Новый раздел** (через Канал A) → сразу добавляется страница + строка `stub`; фиделити
  растёт со временем. `stub` — легальное первое состояние, не долг.

### Что распространять, а что НЕТ

- **Токен** (цвет/отступ/радиус) — распространяется **автоматически**: порт читает
  `assets/tokens.css`, достаточно бампнуть `design_version`. Не запускать ревью 16 экранов.
- **Поведение компонента** — да, правится соответствующий `.vue`, ре-штампуются его разделы.
- **Новый экран / копирайт** — да; структурные разделы могут отставать на штамп без поломки.
- **Закрытие mustbuild-пробела** — только когда серверный endpoint существует; никогда не
  вшивать inert-контрол (honesty-инвариант важнее паритета с макетом).

### Локализация (i18n) — отдельное измерение синхронизации

Перевод на другие языки — требование к запуску, поэтому строки **не зашиты** в шаблоны.
Они живут в `nuxt-port/i18n/locales/<locale>.json`, компоненты читают их через `t()`.
Словарь — это **шов локализации**, ровно как `useMockData.ts` — шов данных.

- **Локали запуска: `ru` · `en` · `zh`** (русский-контракт · английский · упрощённый
  китайский). Каждая — словарь в `i18n/locales/` с одинаковым набором ключей. Добавить
  язык = JSON-файл + регистрация в `nuxt.config.ts` `i18n.locales` (+ правило плюрализации
  в `i18n.config.ts`, если грамматика числа отличается). Переключатель языка в топбаре
  циклит по всем локалям (RU → EN → ZH).
- **`ru.json` — контракт.** Он дословно зеркалит строки макета. Когда макет меняет
  подпись, правится ключ здесь (а не `.vue`), затем ре-штампуются затронутые строки
  `PARITY.json`. `ru` — также `fallbackLocale`: отсутствующий `en`/`zh`-ключ показывает
  русскую контрактную строку, а не сырой id ключа.
- **`en.json` + `zh.json` — образцы перевода.** Расширяются по экрану по мере того, как
  страницы переводятся на ключи; недопереведённый словарь всё равно рендерится (fallback).
- **Плюрализация — правило на локаль в `i18n.config.ts`:** `ru` — славянские 3 формы с
  исключением «надцати» (корректно за 100, в отличие от примера из доков vue-i18n); `en` —
  встроенные 2 формы; `zh` — одна форма + опциональная нулевая («没有密钥»). Счёт всегда
  через plural-ключ + `t('key', n)`, **никогда** ручной склейкой числа с существительным.
- **Реестр готовности к переводу — поле `i18n` в каждой строке `PARITY.json`:**
  `keyed` (всё через `t()`, все три словаря имеют ключи) · `partial` (часть на ключах) ·
  `hardcoded` (литералы в шаблоне — состояние до i18n). Это отдельное измерение, **не**
  дублируется в `gaps` (там — фиделити).
- **Заведено сейчас:** оболочка (`layouts/default.vue` + `useNav.ts`) и `pages/secrets.vue`
  — `keyed`. Остальные 15 страниц — `hardcoded`; перевод на ключи — обычная работа
  «разработчик следует макету», трекается построчно.

Логика та же, что у решения «без codegen»: мы не машинно-переводим UI, а даём один
честный шов (словарь) и один честный реестр (поле `i18n`), чтобы «какие экраны готовы к
переводу» было проверяемо, а не на доверии.
