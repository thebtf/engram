## Identity and resolution

`.engram-project` contains only `{project_id: UUID, name?: string}`. `project_id` is a nonzero UUID in lowercase hyphenated form; `name` is a mutable label of at most 256 Unicode characters with no control characters. The output shape is `project-anchor-v3.schema.json`; the implemented marker reader also limits the file to 4096 bytes. The same UUID is the Project ID in the marker, CLI JSON, gRPC `Project`, HTTP `project`, database, MCP and UI catalog. Names, roots, remotes, branches, installations and authenticated users are not identity. No second server UUID, identity capability, registration approval or resolution audit is required. Ordinary service authentication, privacy, secret handling and effect authorization remain separate and unchanged. An unsigned, untracked marker works; resolution requires neither a clean HEAD nor `git add`.

The central Go resolver consumes the actual host call root. A nearest explicit portable marker is a project boundary; an ordinary subdirectory is not. Git discovery uses the real root and common-dir, including gitfiles, external worktrees, bare repositories, detached and unborn HEAD, sparse/shallow clones. An accepted common-dir ID is a local shared cache, never global identity. A pinned marker/cache resolves offline and without catalog roundtrips. A marker/cache mismatch is `PROJECT_IDENTITY_CONFLICT`; never overwrite it or generate a third UUID. Recorded migration redirects may reconcile a proven mapping in the migration owner.

Only an unpinned selected Git repository with a primary `origin` locator bootstraps the catalog. SSH/HTTPS, standard ports and `.git` suffixes normalize equivalently; case-sensitive paths, nondefault ports and fork origins stay distinct. Credentials are stripped. An upstream, matching basename or HEAD does not identify a project. Remote/path/branch changes after pinning do not change the UUID. Missing marker/cache/locator yields `PROJECT_CONTEXT_REQUIRED`, not a path hash. Non-Git creation requires explicit `engram project init`; browsing a directory never creates a project.

Old name-only markers and complete V3 markers are transition inputs only. Name-only input is replaced with the selected portable UUID after bootstrap; a usable existing UUID is retained. Nothing auto-stages or commits the marker. Independent offline copies lacking shared identity evidence cannot be guaranteed to converge.

## Interfaces

- `engram project resolve --root <actual-call-directory> --json` returns `{project_id,name?}`. Failure emits `{code}` and nonzero exit. JS/TS adapters consume this Go entrypoint rather than compute alternate IDs.
- `engram project init [--name <label>]` explicitly initializes the current directory and returns the same JSON DTO; it keeps an already resolved ID. Unlike `resolve`, its implemented flag set has no `--root` or `--json`. This command does not rotate an existing project ID.
- `POST /api/projects/bootstrap` accepts `{repository_locator: normalized-primary-locator, name?: string}`. An atomic catalog transaction consults proven `project_identifiers` manual aliases first, then existing primary repository bindings. It returns one portable UUID. Ambiguous bindings refuse with `PROJECT_IDENTITY_CONFLICT`; historical non-UUID or dual-key rows require conservation migration (`PROJECT_MIGRATION_REQUIRED`) rather than a duplicate row.
- gRPC `Initialize` / MCP `tools/list` perform no local identity resolution. Missing project context cannot hide the catalog. A scoped call without context alone returns typed `PROJECT_CONTEXT_REQUIRED` while the transport stays alive.
- Normal pinned UUID operations do not invoke V1/V2/V3 resolution, authorization-derived identity or registration/audit roundtrips. Old selectors belong only to conservation migration and explicit unresolved readers, never normal project choices or raw-selector fallbacks. Remove temporary consumer translation after its last supported caller migrates; do not add a permanent compatibility algorithm.

## Independent code state and migration

Shared project knowledge never merges mutable indexes. Preserve Source/Checkout/View, per-session roots, independent dirty snapshots and their existing access checks. A copied marker identifies the same logical project; an intentional new fork/template project requires explicit new identity.

The project catalog uses `project_id` as the selector value and `name` as the label. `POST /api/code/contexts` preserves its existing binding payload and `source_ref`, `checkout_ref`, `view_ref` and indexed-snapshot fields. Its optional `project=<UUID>` filter intersects persisted Source membership with existing code-read authorization; it creates no grant, pin or context. Resolved entries carry that UUID. Retained unresolved entries carry `project_id:null` and `unresolved_reference`, not an invented UUID, raw old selector or silently empty successful result. `GET /api/projects/unresolved/{reference}/code` provides bounded read-only retained membership under the same data/code-read privacy checks. Its existence does not authorize access to another dirty View.

Ops owns proven old selector/locator → retained UUID mappings, complete data/crypto conservation, dry-run, isolated rehearsal and authorized cutover. No basename/hash/upstream merge, semantic memory deduplication, blanket update or discarded unique-key conflict is permitted. Preserve object IDs, versions, timestamps, comments, links, provenance, differing values, global credentials and decryptability, including project-key/AAD bindings. A mixed old selector requires per-record membership, not assignment of all its rows to one project. Unresolved data stays accessible through an explicit review reader with its original privacy checks. Migration must be repeatable after interruption and account for writes between snapshot and cutover; restore must preserve later writes. A project-key change alone does not require reindexing or reembedding unchanged content: retain memberships and snapshots, rebuilding only a derived cache whose key actually changed. Resolver source proof establishes no production migration.
