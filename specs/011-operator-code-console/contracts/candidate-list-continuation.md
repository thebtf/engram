## Wire behavior

A caller requests `GET /api/memory/candidates?project=...&status=pending&limit=100`, reads its existing fields, then sends `cursor=<opaque next_cursor>` with the same normalized project/status and effective limit. The response keeps every existing field and meaning, adding `next_cursor`: a string when more rows exist, or `null` when no further currently visible row exists. Presence of this field is the positive continuation-capability signal; an older server omits it. Null means no next page **at the time of that read**, not a frozen total. `count` remains the number returned on this page. Do not add `total` unless an authoritative count of the same authorized scope and filter is actually computed; omission means unknown. No estimate, loaded row count, or page count is a total.

The UI must parse `next_cursor` by presence and type: absent is legacy, `null` is exhaustion, and a nonempty string is continuation. A present empty string, number, object, array, boolean, or other malformed value is an invalid response: show an error, not legacy or exhausted, and do not use it as a cursor or infer a total.
- Existing requests without cursor retain their defaults, validation, first-page ordering, envelope, status and project semantics, feature gate, and errors. Legacy clients that ignore additive JSON members remain supported; exact-shape consumers must be identified and addressed by the implementation owner before release. Do not change MCP `list_candidates` or other `ListByStatus` consumers as a side effect; keep their semantics and route them through a compatible seam if the store API changes. Old clients that never request a cursor still receive a bounded first page, not an implicitly expanded result.
- An opaque, versioned cursor represents the last emitted `(created_at, id)` key and binds the canonical project, status, effective limit, sort and server-resolved access context. It is integrity-protected and bounded in length; it is neither an authorization credential nor a source of exposed project/privacy data. Apply the strict descending keyset predicate `(created_at, id) < (last_created_at, last_id)`, preserving timestamp precision and the unique ID tie-breaker. A deleted boundary row does not invalidate the keyset. Do not use offsets, client-provided raw keys or a server-side growing snapshot.
- On every page authenticate/authorize again, resolve current access independently, and filter visibility *before* ordering, limiting and lookahead; the cursor grants no authority. Cross-context, changed filter/limit, tampered, malformed, unsupported-version or oversized cursors get a bounded generic 400 invalid-cursor refusal with no candidate data or internal key detail. Authorization failure keeps the existing appropriate denial and no candidate data. A caller whose access changes must restart: if a still-valid subject can no longer access the bound context, refuse rather than follow the old cursor. No fallback to a wider scope or first page on cursor error.
- Fetch at most `limit + 1` authorized rows per page to detect continuation; serialize at most `limit`, derive the token from the last returned row only when lookahead exists. Bound token input, returned size and query work using the existing DB/query context and suitable indexed keyset path. No unbounded server/client accumulation or automatic fetch-all. Handle cancellation/store failure via existing error semantics rather than returning a fabricated empty/end page.

## Mutable data and UI semantics

This is a live keyset walk, not a database snapshot. With an unchanged matching dataset and access, walking until `next_cursor` is null returns each visible candidate once in baseline order, including ties. Concurrent newer inserts ahead of the last key can be missed until refresh; older inserts behind it may appear later. A deletion or status/project/visibility change can remove a row before it is reached; an item newly matching behind the boundary may appear, while one newly matching ahead needs refresh. No total or snapshot completeness is promised across such changes. A changed request filter/sort/limit or access context starts a new walk and invalidates old continuation; the UI clears or explicitly re-confirms selections under `collection-operations.md`, never silently reuses a cursor under another context.

The separate UI owner integrates bounded navigation with existing queue, not a new queue workflow. It must distinguish loading/error/refusal/empty and known-more versus exhausted; an old server without `next_cursor` support cannot be asserted exhausted merely because it omitted a field. The required nullable `next_cursor` field is the explicit positive capability signal; when absent on a legacy server a full legacy page is visibly potentially truncated. Earlier pages may be revisited through bounded page history or refreshed; do not label a last page/total that is unknown. Keep page-size preference local while each request obeys the API cap. Select-all remains a local checkbox operation, labeled as current page and limited to active visible IDs; it does not submit a selected set or perform a bulk mutation. Existing row actions submit only the clicked visible ID through an explicit selection. A navigation `next_cursor` is not the server's `kind=page` selection cursor/token and must never be passed as one. Changing page/filter/context/access or stale rows must not silently enlarge selected targets. Preserve existing action permission/state checks, selection-version checks, action outcomes and unknown-commit handling.

`selection_version` versions the stored selection, not a candidate row. `internal/worker/handlers_candidate_review.go:290-300,400-425` resolves a selection and executes its target IDs; this path does not establish per-candidate `expected_version` enforcement. Feature011 `collection-operations.md:32` retains its expected-version requirement where applicable: the missing candidate row-version enforcement is a separate required dependency owned by the existing Queue mutation/backend owner, to be tracked and proved there. Until that dependency is implemented and verified, do not claim Feature011 candidate row-version acceptance or treat selection-version checks as its substitute. This continuation slice does not silently waive or implement that dependency; pagination acceptance and row-version acceptance remain distinct, and any action requiring the latter cannot be claimed compliant before it is proved.

The current `pages/queue.vue` derives page count/range, `countInFilter`, pending count, promotable count and low-confidence count from loaded `rows`; its `all` (`Все`) page-size option also resolves against loaded rows. Every such surface must identify its scope as current page or loaded rows, or display unknown when an authoritative matching total is unavailable. A page number, range, last-page control, metric, or `Все` must not imply the whole filtered corpus has been loaded. The all option remains bounded by the loaded/page scope and must not trigger unbounded fetch-all. Existing selected-count labels describe local checkboxes, not a submitted mutation or corpus total.

Preserve and extend the existing `useOperatorQueue.ts` request generation/project guard and unmount invalidation to continuation requests: a delayed success or failure from page A must not replace rows, cursors, selection, error or load state after project, filter, access context or effective limit changes, or after unmount. The active generation and current scope alone can publish a result; cancellation alone is not sufficient. Current-page selection uses only the visible IDs of that active page, never rows from a stale response.
