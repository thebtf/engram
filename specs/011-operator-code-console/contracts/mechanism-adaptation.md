# Native Mechanism Adaptation Contract

## Fixed Direction

Engram remains a native implementation over its existing PostgreSQL/pgvector, daemon, worktree, UCI application, and Nuxt surfaces. SocratiCode and Graphify are not embedded applications, deployable services, mandatory dependencies, production subprocess engines, storage authorities, or wholesale source-port targets. Ordinary infrastructure libraries remain permissible when independently selected under Engram conventions.

This contract implements r11 `04-MECHANISM-ADAPTATION.md` for Feature011/R-C interaction. It does not reopen already accepted UCI behavior or make Feature011 wait for a complete inventory of reference features.

## Evidence Record Required for Any New Mechanism or Parity Claim

Before Engram claims new supported-language/relation coverage, reference parity, or imports a new mechanism into the R-C scope, the assigned R-C research handoff supplies one immutable `MechanismAdaptationRecord` containing all fields below:

| Required field | Meaning |
|---|---|
| User task | The real agent/browser task that benefits, not a tool-name match. |
| Reference pin | Product/version/commit plus immutable source URL or local immutable copy identifier. |
| Source behavior | Exact reference files, functions, tests, and where applicable corrected issue/PR evidence that show extraction/chunking, resolution, retrieval/ranking, invalidation, worktree behavior, or context delivery. |
| Reproduction status | Separates read source, reproduced behavior, author claim, and Engram hypothesis. |
| Limits/failure modes | Relevant observed limitation such as alias/re-export ambiguity, stale edge, ignored file, missed invalidation, over-indexing, large-repository bound, or worktree mixing; no issue number alone is proof. |
| Native adaptation decision | What Engram preserves, changes, or omits for PostgreSQL/pgvector, UCI Source/Checkout/View, durable jobs, ACL, browser pagination, and current supported language/profile. |
| Proof | Positive, negative, and known-failure-mode acceptance against source oracle; comparator/baseline availability and any profile differences. |
| Scope claim | Exact supported language/relation/user outcome and an explicit remaining limitation. |

No record is presently supplied to Feature011 for a new reference mechanism. That is a known, bounded dependency: it blocks R-C parity and language-expansion claims, not the limited S1/S2/S3/S4 work over accepted UCI behavior.

## Engram Adaptation Invariants

1. All agent and browser code results use one authorized Source/Checkout/View model. Reusing identical permitted inputs may reuse derived artifacts but never merges mutable worktrees, widens an ACL, creates a shared latest-worktree UI cache, or permits cross-source hash discovery.
2. PostgreSQL/pgvector choices are verified for filtered vector recall, graph traversal bounds, view publication, concurrent updates, revision storage, pagination, and recovery; the database is not presumed faster or semantically superior by declaration.
3. One requestable browser result ties semantic search, bounded graph, and exact source to the same View. Code Explorer displays partial/unsupported/stale limits rather than translating a graph count into a correctness claim.
4. Reference comparison uses aligned source corpus/ignore policy/profile when possible and states unavoidable model/budget/profile differences. Lexical baseline, source oracle, and independent review judge correctness; an unavailable comparator means parity is unverified, not that Engram is defective.
5. No code corpus is sent to an unapproved provider; isolated reference execution requires authorization and does not install hooks or alter active profiles.

## Bounded R-C Comparison Basis

Before R-C optimization, its owner freezes a small source-oracle-reviewed task set: exact identifier, Russian conceptual query, cross-file dependency, impact, reverse path, worktree switch, and deliberate no-answer. The set is run against Engram and an aligned lexical baseline; pinned SocratiCode/Graphify comparators are added only when an authorized isolated environment makes their matching capability/profile available. Each result records View/source correctness, relation correctness or limitation, retrieval mode/coverage, useful-result latency, cold/warm/update condition, and tool/context/embedding cost where applicable. Node/edge totals never substitute for this comparison. The fixed set may evolve only through a documented user-task change or source-oracle correction, not because an implementation needs an easier score.

## First R-C Scenario Binding

The R-C owner evaluates the two-worktree scenario required by r11: in worktree A an aliased/re-exported function changes while an importing caller remains textually unchanged; worktree B has a different function version. The evidence must establish direct/reverse relations, invalidation of affected A resolution, absence of stale A target, B stability, and exact source read from each View. Node/edge counts or a named relation alone do not close this scenario.

Feature011's HTTP/browser contract consumes the resulting UCI response only. It does not choose extractor implementations, re-indexing mechanics, parser bundles, vector providers, graph algorithms, or reference integrations.
