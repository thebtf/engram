## Task Format and Traceability Rules

- Every task names its precise source file or directory, requirement IDs, prerequisite IDs, owner boundary, focused proof, and atomic-commit condition.
- `[P]` appears only where the named files are disjoint and every listed dependency is already complete; it never authorizes concurrent edits to a shared file.
- `Owner boundary` names the code or evidence surface that owns the work; it does not assign a person, role, queue packet, or authority outside that surface.
- Each code, test, fixture, or evidence slice is committed atomically after its listed proof. A later release/acceptance task does not absorb unfinished focused slices.
- `legacy_unscoped` code-index rows remain explicit compatibility/rollback data. No task may invent a Source, Checkout, View, HEAD, privacy scope, or authority from a raw project string, path, branch, label, remote, or hash.
