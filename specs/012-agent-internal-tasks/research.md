## Decisions

### R1 — One card, not another task system

**Decision**: Extend existing Issue/IssueComment and their current readers/lifecycle. Owner/recipient are optional opaque labels; target is routing/filtering, not authority. Resume uses an explicit task-relevant list/get on a fresh consumer.
**Rationale**: `models.go:261–294` already owns durable cards and comments. Native and OpenClaw already expose issue operations; both UIs edit the same REST records.
**Alternatives considered**: A task table with its own lifecycle, scheduler or automatic inbox producer would duplicate accepted authority and exceed the requested slice. DAG UI stays deferred under the trigger in spec.md.

### R2 — Receipt equality is original-payload equality, after authorization

**Decision**: Unique (decided existing actor identity, canonical source project, opaque request_key) binds one issue to original canonical logical payload v1 through its server-normalized SHA-256 binding stored only in the issue receipt. Main comments 1730/1739 provide narrow retry policy and Engram session 01a18a3b chose this DB representation under comment 1742’s delegated authority. Authorize/read before lookup/replay/comparison; equal original payload in the same namespace replays one ID, mismatch reveals no original field/hash/ID, different actors stay isolated. Binding is not privacy proof and is never exported to logs/review/telemetry/embeddings or knowledge/similarity processing. Secret/vault exclusion remains policy, not a claim that current issue routes already detect secrets.
**Rationale**: current CreateIssue inserts without retry identity; REST body source and native transport-derived source do not authenticate authorship. Existing UUID syntax resolution is not active canonical existence: Engram session 01a18a3b selected existing SessionStore.CanonicalProjectExists plus existing authenticated actor/read context. Native local root resolution remains meaningful origin evidence; no source ownership claim or new principal ACL follows. These source facts motivate the recorded actor+canonical-source receipt namespace, not an unresolved product choice.
**Alternatives considered**: Title matching is not intent identity. Keying by target or claimed source enables aliasing/disclosure. Comparing only a digest does not authorize private-content processing. Reusing the card's current fields makes a retry fail after a legitimate edit.

**Scoped precedent, not transferred authority**: session-evidence-intake.md:25–29 forbids plaintext-credential fingerprints to admit evidence; it governs a different domain. Main’s accepted issue-specific clarification now supplies its own narrow retry policy, not permission for secrets/vault material, global processing or new raw private-history snapshots. Earlier bounded policy-not-found evidence predates that clarification and is not a current general blocker.

### R3 — One revision transaction, all writers

The R3/R4 decision text below records the earlier design. Main's later accepted clarification permits standalone resolve/reopen/close without a caller revision under the locked transition rules in `contracts/issues.md`; field edits and supplied revision preconditions remain strict. Unconditioned lifecycle calls cannot prevent an intervening-state-cycle ambiguity.

**Decision**: Material updates require an expected integer revision (wire decimal string), authorization rechecked under lock, and one fields/state/history/optional-comment commit. A comment-only append is independent and does not increment issue revision. Existing bulk/selection actions retain their atomic set semantics while adopting per-target issue revisions. Internal conditional acknowledgment records its actual system actor; no new producer is introduced.
**Rationale**: `issue_store.go:297–377` already groups PATCH effects but has no CAS; `492–630` shows acknowledgment and selection as real alternative writers. Selection currently checks timestamps, so a field-only CAS patch would leave a bypass.
**Alternatives considered**: Timestamp-only general CAS is weaker than the accepted monotonic revision contract. Retrying a losing edit with an automatically refreshed revision silently overwrites the winner. Appending a losing compound comment violates the requested no-op.

### R4 — Bounded compatible projections, explicit breaking edit admission

**Decision**: Keep REST limit/offset, add it to native/OpenClaw, add text/owner/recipient filters server-side, and bound detail/history/comments separately. Preserve completeness, not an unbounded default: old unpaged readers get complete comments within a finite response budget or DETAIL_PAGING_REQUIRED, never a first-page success. Native/OpenClaw text and both UIs explicitly cut over to detail_mode=paged, show loaded range/total/complete status and continuations, and keep a lossless JSON mode. Updated UIs retain one key per pending create and the read revision per draft. Missing revision produces a precondition error; legacy unkeyed creates remain explicitly single-shot.
**Rationale**: REST/store already implement limit/offset and stable priority/date/ID ordering; native `tools_issues.go:328–403` has max 100 but no continuation, and native/OpenClaw text projections omit structured fields. Console already requests 200, so a universal cap of 100 would regress a current reader. `OpenClaw client.ts:680–681` currently collapses errors to null; it cannot support truthful CAS without typed failure mapping.
**Alternatives considered**: Client-side filtering of page one misses the task. A metadata-wide index changes scope and privacy. A cursor subsystem is unnecessary for the existing mutable inbox: document live offset paging rather than pretend snapshot completeness.

**Engram session 01a18a3b engineering choices / cited evidence**: HTTP requestBodySize uses 10 MiB (middleware.go:276–285); ordinary server/native pool gRPC limits are 16 MiB (server.go:83–85, engramcore/grpcpool.go:190–193), not standalone MCP Scanner. List 200 follows collection/console use; defaults remain HTTP 50/native-OpenClaw 20. New comments/history defaults 50/max 200 and 4 MiB serialized-page target are issue-owner decisions, with 4 MiB one quarter of native 16 MiB, not HTTP response cap. Return continuation before target overflow; intact oversized singleton where transport permits, safe native-envelope error with retained authorized REST read otherwise. Legacy full comments ≤200/4 MiB or explicit paging required. Metadata compact JSON ≤1 MiB/depth 256 are explicit new bounds consistent with bounded UCI/consolidation patterns; Engram session 01a18a3b observed Node v24.22.1 successfully round-tripped 256 containers. Key UTF-8 nonempty/≤512 bytes/no NUL uses existing issue cursor budget (handlers_issues.go:1164,1171), not its encoding/alphabet. No new title/body/labels restriction or historical byte loss.

### R5 — Expand and preserve; no destructive rollback

**Decision**: Add metadata/revision and dependent receipt/history records, assign a truthful baseline to old issues, preserve old comment IDs/text, and cut over all writers under a bounded writer pause. Downgrade only to a writer that preserves revision/history or keep writes held; preserve the expanded database and use forward repair after feature writes.
**Rationale**: Existing rows do not contain historical actor/revision evidence. Fabricating a sequence or dropping new data on rollback violates Constitution X. Migration numbers must come from the live registry at implementation time, not this draft.
**Alternatives considered**: Copying rows to a task table risks ID/provenance loss. Letting old unconditional writers run after backfill makes revision/history untrustworthy. No rollout flag can conceal that defect.
