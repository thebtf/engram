## Representative caller

Goal: save one internal task and resume it later without overwriting another writer. This synthetic request contains no private data. The ordinary native client resolves source locally from its caller/worktree context; current REST/UI callers submit source attribution, and checked server UUID validation does not itself verify source authenticity. The design requires canonical existence/admission in existing authenticated actor context. Authentication is separate from these source/author fields; this example does not claim every current transport already proves a trusted source binding:

`issues({action:"create", format:"json", request_key:"513-demo-intent-1", target_project:TARGET, title:"Document retry recovery", body:"Record the observed outcome and next action.", type:"task", priority:"medium", labels:["internal"], owner_label:"docs", recipient_label:"next-agent", metadata:{acceptance:["same issue after restart"], outcome:{state:"pending"}}})`

Proposed success data: `{id:701,revision:"1",replayed:false,message:"issue created"}`. After a lost reply, repeat the same intent and key: `{id:701,revision:"1",replayed:true,message:"issue replayed"}`. IDs are examples, never fixture/live evidence. A later legitimate edit may make the replayed revision newer; comparison still uses the original create payload. Call get before deriving an edit.

## Shared values and bounds

- IDs remain existing positive issue/comment numbers. Revision/expected_revision are canonical decimal strings representing integers 1 through 9223372036854775807; reject zero, signs, fractional/rounded numbers and overflow. Do not wrap revision on exhaustion; fail without mutation.
- Types: bug, feature, improvement, task. Priorities: critical, high, medium, low. Statuses retain open, acknowledged, resolved, reopened, closed, rejected and existing action-specific authority/transition rules.
- `metadata` and `comment_metadata` are objects, not null/arrays/scalars. Create/comment omission defaults to {}; patch omission leaves unchanged and {} replaces the complete object. Preserve unknown admitted keys/values, never interpret them as target/control/auth. Compact JSON ≤1 MiB and at most 256 nested containers (the metadata root counts as the first container) are explicit new issue-owner bounds. Reject unsupported numbers/received raw duplicate members/oversize/depth before mutation; do not silently redact/truncate metadata or alter historical readable bytes.
- **Decided request/key limits**: retain the actual ordinary HTTP request ceiling 10 MiB (`internal/worker/middleware.go:276–285`) and ordinary native gRPC receive/send envelopes 16 MiB (`internal/grpcserver/server.go:83–85`, `internal/handlers/engramcore/grpcpool.go:190–193`). The separate ordinary mux IPC recipient is pinned to muxcore v0.29.1: `owner/resilient_client.go` `runIPCReader` has a 1 MiB Scanner maximum. Measure the complete final dispatcher response plus its newline against that recipient, after actual proxy text wrapping; it is not a persistence/body/metadata cap or the standalone MCP Scanner. New request_key is opaque nonempty valid UTF-8, at most 512 UTF-8 bytes, with no NUL; reject invalid UTF-8/NUL/oversize without writes. The 512-byte choice reuses issue collection cursor budget (`handlers_issues.go:1164,1171`), not its alphabet; there is no new ASCII-only key rule. No separate new title/body/labels caps: keep existing semantic validation and transport ceilings, preserve historical reads. Metadata 1 MiB/depth 256 are explicit new bounds, not claims about the old issue schema; 1 MiB follows bounded UCI/consolidation patterns and Engram session 01a18a3b observed Node v24.22.1 successfully stringify/parsed 256 containers. This provenance correction reruns no diagnostic.
- Owner/recipient absent or null means unassigned; null on PATCH clears it. Empty owner/recipient string is invalid. Body may be explicitly empty on patch; an omitted field remains unchanged. Labels [] clears labels. Title cannot be empty. Source/target/creator attribution cannot be rewritten by a general field patch.
- **Decided internal actor namespace**: SourceClient uses its existing KeycardID, not a per-agent key or free-form principal label. A validated persisted browser subject uses its user ID via the existing session/browser identity path; never infer a human from source_agent or an unvalidated body. Otherwise represent authenticated master, HMAC session and auth-disabled operator as separate source-qualified singleton actors (`operator:master`, `operator:session`, `operator:auth-disabled`), honestly synthetic/non-human rather than fabricated users. Namespace types remain disjoint from client and browser IDs. Missing/invalid required authenticated identity follows existing denial, never a fallback that broadens authority. Returned actor descriptor remains {kind:client|operator|system|unknown,reference:string|null}; release only policy-approved non-secret references, not token/keycard credentials. Submitted authorship/source/session labels remain separate.

For the new resumable journey, callers generate one key before the first submission and retain it with the unmodified pending payload until outcome reconciliation. A refresh/retry of that intent reuses the key. A deliberately new task uses a new key. Legacy unkeyed create remains a single-shot create, with no replay guarantee and `replayed:false`; no server-generated pretend key is supplied.

Unknown/non-comparable descriptors cannot authorize automatic retry. Preserve the original pending actor/expectation/key/source/payload on ACTOR_CHANGED and require explicit reconciliation. This supplements, rather than replaces, the all-caller key-retention and unkeyed behavior above.

Validate a supplied authenticated-subset descriptor; unknown or null/unavailable/non-comparable references cannot masquerade as stable identity or compare equal, and system is not an authenticated self-description kind. The same trusted receipt/CAS actor owner independently captures one immutable server-derived actor and its authenticated descriptor. A well-formed mismatch/non-comparable expectation returns generic ACTOR_CHANGED HTTP 409 with safe reconciliation guidance and no issue ID, actor identity, payload or hash; perform no receipt lookup/insert or issue-domain write. Malformed descriptor input retains existing INVALID_ARGUMENT handling after ordinary admission precedence. This is only the extra guarded-request precondition before the unchanged execution-order clause below, not a replacement for existing authorization, visibility, input/privacy validation or namespace rules. Omission preserves existing behavior and adds no requirement to unkeyed creates.

The focused #513 race oracle switches authentication between actual GET auth-me and keyed POST while retaining the original pending actor/expected_actor/key/source/payload. Require generic ACTOR_CHANGED with no new issue/receipt or receipt lookup/insert reached, even when the new actor could independently create. Prove normal authentication/authorization and canonical source admission failures keep precedence, unknown/null cannot compare equal, unchanged comparable actor succeeds/replays, and omitted expectation/unkeyed behavior remains unchanged. The guard and transaction namespace must share the same immutable server-derived actor. Preserve actual master-versus-HMAC auth-me RED with identical legacy admin fields, persisted-browser/keycard/noauth coverage and no-secret-disclosure checks; obtain GREEN during #513 implementation, not in this contract-only update.

Execution order: authenticate the decided existing actor; resolve native source locally and check active canonical existence/admission with SessionStore.CanonicalProjectExists in that actor context; establish ordinary create and read/visibility scope **before receipt lookup**, replay or comparison. Validate received raw JSON, limits, admitted numeric values and applicable recognized-secret protections without modifying logical input. Lookup only (actor_identity_key,canonical_source_project_id,request_key). On a receipt hit, recheck current issue read visibility/authorization before computing/comparing the v1 original-payload binding and releasing any result. Same namespace/equal binding yields original ID; unequal binding yields generic conflict without original field/hash/ID. Never look up/disclose another actor’s receipt; independent creation uses existing authority. Atomically publish issue, initial revision/history and receipt binding. Insert races reconcile only within this namespace. Before-commit failure leaves no partial effects; lost committed response uses the same actor/source/key and original payload, not current edited issue.

**Canonical logical payload v1**: server resolves admitted canonical target and applies defaults; type uses current trim/lowercase rule, priority remains valid enum; title/body retain exact Unicode and whitespace; labels form a de-duplicated sorted set of exact strings; include owner_label/recipient_label with null and full admitted metadata. Object order is irrelevant, array order significant, and equal number forms such as 1 and 1.0 canonicalize together. Encode deterministic canonical JSON using simple standard-library primitives; SHA-256 is stored only as original-payload binding in issue receipt, never exported. Actor/source/key are the receipt namespace, not mutable logical content; source-agent/session attribution is separate. No serializer framework.

Optional expected_actor is excluded from the original canonical logical create payload and its v1 hash. Adding or omitting the guard does not change logical-payload equality or rebind a receipt; it never supplies authentication or authority.

Retained issue attribution adds `target_session` as a logical recipient reference, not an actor or permission. A keyed create with no target session keeps the exact v1 binding for retained receipts. A nonempty target session uses a v2 binding containing the v1 payload and exact target session; a different recipient conflicts. Never rewrite a retained receipt or its original binding. The actual target ledger and any existing receipt constraints must be checked before the migration is applied.

**Decided numeric/wire boundary**: received JSON numbers, including metadata, must be finite IEEE-754 binary64 values whose incoming decimal numeric value survives binary64 → shortest decimal → numeric-value comparison; integers additionally lie within ±(2^53−1). Check raw received numeric tokens before mutation, rejecting nonfinite/overflow/unsafe integers and underflow/rounding that changes decimal value. Raw 9007199254740993 and 0.10000000000000001 are rejected; 1/1.0 canonicalize together. Duplicate received raw members anywhere are explicit errors. A TypeScript object parsed/rounded before transport cannot reveal earlier duplicate keys/original number spelling: validate the actual wire, never claim a mythical cross-platform serializer recovers lost input. Use simple standard-library primitives, no serializer framework.

Success: first create HTTP 201; same actor+canonical source replay HTTP 200; data {id,revision,replayed,message}. Never return creator credentials, original receipt payload or digest. Different actor or canonical source has an independent namespace, with independent create admitted only by existing authority and no disclosure/reuse of another actor’s result. Same-namespace original-payload retry after edit returns the same ID/current authorized revision. Deleted-card binding gives safe ISSUE_GONE without resurrection/new ID/deleted body; permission failure takes precedence.

The retained issue-attribution contract also requires exact `source_session`, `participant_session`, and `target_session` list filters. `participant_session` matches recorded creator, comment, lifecycle event or committed material-revision attribution. For mutation attribution, a transport session takes precedence over explicit `session_id`; when neither is present, the existing bridge retains reported `created_by_session` as a compatibility fallback. All of these session values and precedence rules are provenance only, never authentication or authority. An invalid nonempty selector fails instead of broadening the query; filters combine with the authorized issue scope before counts and paging. With the updated ordinary native shim and daemon together, a host session absent for one client remains absent for issue attribution; it is not borrowed from the shared daemon. Pagination: `limit` 1–200; omitted HTTP limit=50, native/OpenClaw=20. `offset` is a nonnegative in-range integer, default 0. Invalid bounds/types are errors, not silent defaults. Preserve existing priority rank ascending, created_at descending, id descending order. Response `{issues:[summary],total,limit,offset,next_offset:number|null,project_names:{canonicalID:displayName}}`. Summary includes id, revision, title, status, priority, type, source/target project roles/origin, source_agent, owner_label, recipient_label, labels, timestamps and comment_count. This is live offset paging, not a frozen snapshot: concurrent insertion or changed rank can move rows. Keep filters fixed, de-duplicate IDs while browsing, and restart after material refresh; do not promise all-row uniqueness across a changing corpus. Static 205-card proof must reach later pages completely. Bulk selection retains its existing frozen/explicit-selection owner rather than adopting inbox offset as authority.

REST `GET /api/issues/{id}`; native/OpenClaw action=get. Current consumers explicitly request detail_mode=paged. Comments and history each default to 50 records, maximum 200; offset defaults to 0. Each comments/history page uses a **4 MiB serialized-page target**, a new issue-owner budget equal to one quarter of observed native 16 MiB, not an existing HTTP response cap. Stop before exceeding the page target and return continuation to the first unreturned record; no silent truncation, skipped record or empty-page loop. A single historical record exceeding 4 MiB is returned intact as a singleton with explicit oversized indication when the real response transport permits. Enforce the actual serialized native 16 MiB envelope including framing/other fields and the final 1 MiB ordinary mux IPC frame independently; if either actual recipient cannot carry the intact response, return a safe explicit error and retain authorized REST access. Existing historical issue/comment bytes are never trimmed/lost to meet a target. Existing optional REST project scope remains unchanged. Paged response:

- `issue`: existing authorized detail fields/project roles/origin plus metadata, revision, owner_label, recipient_label and known actor descriptor where allowed; no creator keycard secret.
- `comments`: ascending created_at/id, objects `{id,issue_id,author_project,author_agent,body,metadata,actor,created_at}`.
- `history`: ascending revision, objects `{revision,previous_revision:string|null,action,changed_fields:[string],actor,attribution:{source_project:string|null,source_agent:string|null,session:string|null},created_at,changes:object}`. Only policy-authorized before/after values appear in changes; absent historical values remain unknown, not empty invented values. The same issue authorization covers this entire projection.
- `history_events`: separate ID-ordered lifecycle events, read with exclusive `history_after_id` and bounded continuation `history_has_more` / `history_next_after_id`. These are not material revision records; absent historical attribution and verification remain unknown. Lifecycle event, corresponding revision and optional comment must commit in one transaction.
- **Paged-detail request arguments**: `comments_offset` and `history_offset` are nonnegative integers, each defaulting to 0. `comments_limit` and `history_limit` are integers from 1 through 200, each defaulting to 50. Invalid values fail explicitly; the existing authorization and transport rules are unchanged.
- **Paged-detail response fields**: retain `comment_count`, `history_count`, `comments_next_offset`, `history_next_offset`, `comments_complete` and `history_complete`. Add effective `comments_offset`, `comments_limit`, `history_offset` and `history_limit`; these report the admitted/defaulted request values, not the number of items actually returned under the byte target. Counts cover authorized records only. Preserve existing authorized display-name fields.
- **Derived ranges, not additional wire fields**: comment and history ranges are the zero-based half-open intervals `[comments_offset, comments_offset + len(comments))` and `[history_offset, history_offset + len(history))`. Derive them from the effective offsets and returned arrays; do not serialize a duplicate range object. A UI may display nonempty intervals as 1-based ranges. When the corresponding array is empty, show an empty range, including at a nonzero offset.
- **Oversized indicators**: add boolean `comments_oversized` and `history_oversized`. Each is true only when its corresponding collection returns one intact record exceeding the 4 MiB serialized-page target; otherwise it is false. The existing intact-singleton, actual native-envelope error and authorized REST-access rules remain unchanged.
- **Continuation and completeness**: each next offset is the first unreturned record (the corresponding range end when later records remain), or null when none remain. Each complete flag means no later records remain for that collection in this response, equivalently its next offset is null; it does not assert that a client starting at a nonzero offset has loaded earlier pages. Clients derive display ranges from these canonical values and track their own accumulated pages. This live offset DTO promises no snapshot paging and changes no legacy/unpaged behavior.

**Full-comment compatibility and cutover**: legacy unpaged detail returns all authorized comments only within **200 records and 4 MiB serialized comments** and the actual transport envelope; otherwise DETAIL_PAGING_REQUIRED without partial success/comments array. Recovery names detail_mode=paged and continuation arguments. Historical oversized records remain intact singleton reads on paged transport where possible; a native-envelope refusal retains authorized REST access rather than removing data. This is explicit admission/cutover, not silent first-page success or a new HTTP response cap.

Read visibility and canonical-project selection are distinct: neither caller labels nor query project confer access. Use existing configured authentication/authorization, including an explicitly configured operator/no-auth realm where that is already supported, not a new blanket public-read policy. Denied/not-found target yields the same body-free not-found result under the existing reader policy; suppress metadata, actor references, counts and receipt existence.

## Refine, progress and comment

REST `PATCH /api/issues/{id}`; native/OpenClaw action=update expands to material fields as well as existing resolved progression. Input `expected_revision` and any present title/body/priority/type/labels/metadata/owner_label/recipient_label/status; optional `comment` and `comment_metadata` belong to the same transaction. No source/target/creator-field edit is added. At least one edit/state/comment must be present; comment_metadata without comment is invalid.

Protected material fields retain creator-keycard/operator authorization. Authorized read-write participants may resolve, close or reopen; resolved means awaiting verification, and reopen accepts resolved or closed. Operator-only acknowledgment/reject/open transitions retain their restrictions; actor labels and reported session provenance cannot elevate authority. In mixed requests apply the strictest required action authority. Validate/recheck under the issue row lock, compare caller's expected_revision, then commit changes/revision/history/comment together. Success HTTP 200 data `{id,revision,changed:boolean,comment_id:number|null,message:"issue updated"}`. Same-value material request with current revision is a no-op unless it includes a real comment. A stale expected revision conflicts even if the proposed field value now matches; do not auto-rebase.

Example: `{expected_revision:"1",body:"Observed recovery; next verify the installed consumer.",metadata:{outcome:{state:"partial"}}}` succeeds with revision 2 and one attributed change. A concurrent request still based on 1 gets REVISION_CONFLICT and its optional comment is absent. A current readable revision may be included in that error only after authorization; the UI retains both its original base and draft, offers a fresh read, and requires an explicit user/agent decision before resubmission. Do not preserve two conflicting field payloads by claiming both committed.

Standalone comment: native/OpenClaw action=comment with id, body, metadata; REST existing PATCH with comment and comment_metadata only. Nonempty comment body required. Return HTTP 200 data `{id,revision,changed:false,comment_id,message:"issue updated"}`; comments append and do not change issue revision. A supplied expected_revision is honored; absence on comment-only append does not authorize a material edit. Native action=comment rejects submitted title/priority/type/status/labels/owner_label/recipient_label instead of forwarding them as material updates; use action=update for compound material edits. No standalone-comment deduplication is promised.

Native/OpenClaw reopen/close retain action names but require expected_revision and current authority. Map reasons/metadata into the same transaction. Existing HTTP acknowledge/selection/delete and internal conditional acknowledgment must participate in shared revision/history or equivalent conditional-state enforcement, not bypass it. Selected material actions carry per-target expected revisions and preserve all-or-nothing/no-content failure semantics of the existing selection API. Keep the existing deletion policy, add no delete capability, and preserve receipt non-resurrection. Legacy timestamp selection input can only resolve a revision after its original binding/timestamp check against the locked row; it cannot refresh a stale draft silently.

## Errors and safe recovery

REST JSON error data: `{error:{code,message,...safeDetails}}`; native/OpenClaw JSON mode preserves that same object; text mode includes the stable code and recovery action without protected data. Do not collapse errors into null, success text, a duplicate create, or an unconditional retry.

| Code | HTTP | Meaning / caller action |
| --- | --- | --- |
| INVALID_ARGUMENT | 400 | Invalid enum/object/field/bound/normalization input; correct it before retry; no writes. |
| PAYLOAD_TOO_LARGE | 413 | Existing request/envelope or new metadata/key/depth bounds exceeded; no truncation or write. Historical page-target overflow alone uses continuation/intact-singleton behavior, not deletion. |
| UNAUTHENTICATED | 401 | Existing auth required; no issue/receipt lookup disclosure. |
| FORBIDDEN | 403 | Current actor lacks the requested mutation; no payload/count/replay or CAS details. |
| ISSUE_NOT_FOUND | 404 | Missing or unreadable card under the existing reader policy; no history/comment leak. |
| ACTOR_CHANGED | 409 | Supplied keyed-create actor expectation is unequal or non-comparable. Generic error only: no issue ID, actor identity, payload or hash; no receipt lookup/insert or issue creation. Preserve original draft/intent and reconcile explicitly, never silently retry under another actor. |
| IDEMPOTENCY_CONFLICT | 409 | Same authenticated actor + canonical source + key, different original logical payload; no ID/field diff/payload/hash. Reconcile original intent, never auto-create another key/card. |
| REVISION_CONFLICT | 409 | Caller base lost; no request effects. Optional safeDetails.current_revision only after current read authorization; read and explicitly reconcile while retaining the draft. |
| INVALID_TRANSITION | 409 | Existing lifecycle precondition fails; read current card and choose a permitted transition. |
| REVISION_REQUIRED | 428 | Material mutation omitted expected_revision; upgrade/use a current reader, get revision, then retry the intended mutation. No blind fallback. |
| ISSUE_GONE | 410 | Authorized retained receipt points to an explicitly deleted issue; no deleted body and no new ID. |
| DETAIL_PAGING_REQUIRED | 409 | Legacy complete comments exceed 200 records/4 MiB or complete detail cannot fit its transport; no partial success. Use explicit paged detail and separate continuations. A record that cannot fit native envelope gets safe TRANSPORT_RECORD_TOO_LARGE guidance retaining authorized REST access. |
| PROJECT_* identity/migration error | Existing typed status | Preserve existing exact recovery guidance and project-free authorized reads; no source/target substitution. |
| PRIVACY_REJECTED | 400 | Applicable existing protection recognized disallowed secret material in a new issue write; reject atomically without value/field/digest disclosure or silent metadata redaction. This is not a claim of comprehensive detection. |
| TRANSPORT_RECORD_TOO_LARGE | 413 | An intact response cannot fit the actual native 16 MiB gRPC envelope or the final 1 MiB ordinary mux IPC frame after proxy/dispatcher escaping; retain authorized REST detail/paging access and original bytes. |
| UNAVAILABLE | 503 | Dependency unavailable, no claimed commit; reconcile keyed creates with original actor/source/key after recovery, never blindly retry unkeyed create/comment. |

Error mapping changes are intentional compatibility work. Existing plain human native output remains default; proposed `format:"json"` returns one lossless serialized JSON result inside the current MCP text-content envelope, not a new transport. OpenClaw advertises and validates the same mode/fields. Both UIs render stable codes, preserve drafts on 409/428/unknown outcomes and never discard a create intent until reconciliation. Metadata, body, comments and history remain quoted data in agent output and escaped data in UI; they cannot inject host instructions.

HTTP keeps its existing 10 MiB request ceiling; native keeps its actual 16 MiB envelope. The shared owner does not add a title/body/labels or HTTP response cap.

For native comment/reopen/close argument renaming, first call `issues.DecodeReceivedObject(receivedRawJSON)`: it refuses duplicate members, unpreservable numbers and invalid Unicode before returning exact raw member values. The gRPC canonicalizer applies this admission to the original issue arguments before any compatibility-project map rewrite can erase received evidence. Rename comment/reason `body` to `comment` and its `metadata` to `comment_metadata` as appropriate for the existing action, then serialize with `issues.EncodeReceivedObject` and call `Application.Mutate`. That raw-member encoder disables HTML expansion; the worker bridge uses it too, so valid compact metadata does not become oversized merely through internal wrapping. Do not pass a native standalone-comment body or extra material fields as issue edits. These helpers grant no authority and do not replace the application's authentication, source, DTO, metadata-bound or privacy checks.

DTO member names are case-sensitive: alternate case-folded names are refused before struct decoding or native remapping, including `expected_actor.kind` and `expected_actor.reference`. This rule does not inspect or rename unknown metadata keys. Only an omitted `target_project` defaults to the admitted source; an explicitly empty or null target is invalid and creates no issue or receipt.

`Scope.SourceProject` is the existing resolved canonical source attribution; `Scope.ReadProject` is empty for existing project-free authorized access, or an exact canonical project narrowing the existing source/target-role reader. Neither field establishes principal ownership. The owner captures `auth.IdentityFrom(ctx)` once, checks existing mutation authority and canonical admission before the actor guard, and repeats admission/current-row authority in the transaction. `issues.CaptureActor(ctx).Descriptor()` is the corresponding auth-me projection seam; adapters must not reconstruct it from role, cookie, agent or expected_actor fields.

`CreateCommand`, `MutationCommand`, `Result`, `ActorDescriptor` and stable `Error` are exported through `internal/issues`; their authentication/database-independent definitions live in `internal/issues/contract` because the existing `auth.Validator` already imports GORM. Create returns `{id,revision,replayed,changed,comment_id,message}` with revision as a decimal string. Mutation uses presence-sensitive pointer/raw fields, allowing explicit empty body, empty labels and nullable owner/recipient labels; it returns one optional committed comment ID. Comment-only requests can omit expected_revision; every material request requires it. Source/target/creator attribution is not a general editable field. Typed errors expose only code/message and authorized `current_revision` for a CAS loser. Transports wrap these as the existing `{error:...}` DTO and map the status table above; they must not wrap database errors or log raw JSON/receipt bindings.

`IssueStore.AdmitTaskScope`, `CreateTaskIssue` and `MutateTaskIssue` implement the persistence contract for this application, not alternate adapter entrances. Original-payload binding and receipt keys remain private, SQL logging is suppressed on these transactions, and material history contains field names with empty `changes`, never before/after payload snapshots. T008 composes the HTTP create/PATCH and auth-me paths with these owners; native and remaining bulk/internal/delete writer cutovers retain their separate assigned stages. No complete writer cutover or ordinary-consumer acceptance follows from this HTTP composition alone.

## T008 HTTP and shared read composition

HTTP list/detail use `IssueStore.ListTaskIssues(ctx, IssueTaskListParams)` and `ReadTaskIssue(ctx, id, IssueTaskDetailParams)`. These APIs are also available to the later native adapter. The list selects summary columns only and applies literal title/body search, exact labels, independent canonical source/target filters and bounded SQL paging before returning a page. Detail authorizes the existing optional canonical read scope before counts or collection reads. Independent comments/history pages are streamed under a repeatable-read transaction, bounded by SQL limit and the exact serialized 4 MiB collection target; an intact oversized singleton retains explicit continuation. Legacy complete comments fail with `DETAIL_PAGING_REQUIRED` rather than partial success when their count or bytes exceed the compatibility bounds. Native's actual envelope check remains its adapter responsibility; HTTP introduces no response cap.

Existing HTTP PATCH requests may omit caller source attribution. In that case the shared mutation owner authorizes and locks the current issue, admits its existing canonical source, and records unknown caller source attribution instead of inventing it from the card. Supplied attribution still requires ordinary canonical admission. Neither path changes creator/operator/collaborator authority, skips expected_revision for material changes, or rewrites source/target/creator fields. These are compatibility semantics, not a new scope selector or bypass flag.

## T010 native composition and proof boundary

The native `issues` adapter preserves received raw members through shared duplicate/numeric/Unicode admission before renaming comment/reason fields. It pins the existing authenticated identity, uses the transport's canonical source (never a submitted compatibility project), and calls the same application and bounded read APIs as HTTP. `agent_source` remains a compatibility attribution alias for `source_agent`, not a second authority. Transport session attribution comes from the existing session context. The 1–200 list bound intentionally replaces the old native 100-record maximum; metadata and material revision rules do not gain a native-only bypass.

Default text get explicitly selects paged detail and reports independent comments/history ranges, total, complete/oversized state and exact next calls. JSON get without detail_mode retains the explicit legacy complete-comment compatibility rule; JSON paged detail returns the full admitted DTO inside one MCP text block. Typed issue failures, including the central read-only refusal, retain their safe code/message in public JSON-RPC error data; missing reads name authorized list recovery. An early `*issues.Error` from original raw gRPC admission is serialized as the same ordinary issue error object in `CallToolResponse{is_error:true}` before any map rewrite or handler call. The existing native proxy therefore preserves `result.isError` and structured `data.error.code` instead of converting safe duplicate/numeric refusal into generic JSON-RPC -32603. Other tools and existing transport/auth/project errors retain their original status paths and precedence. SQL/private payloads are never wrapped into native errors.

Before releasing a successful issue response, the native public server measures the actual escaped MCP content and the protobuf CallToolResponse fields against the existing 16 MiB envelope, conservatively including the five-byte gRPC frame, and checks terminal JSON-RPC serialization too. Independently, the ordinary dispatcher measures the actual final issues response after engramcore proxy text wrapping; response plus newline must fit the pinned muxcore v0.29.1 recipient's 1 MiB Scanner buffer. Either over-limit intact response yields TRANSPORT_RECORD_TOO_LARGE with authorized REST paging guidance, no partial result and no stored-data mutation. The IPC guard replaces only the wire result with the same safe issue error object and is not a new storage bound or silent truncation. Focused proof crosses the real pinned owner/resilient recipient, dispatcher, proxy and loopback authenticated gRPC service; installed/profile-launched client acceptance remains an explicit T019 obligation. Remaining bulk/internal/delete writers retain T018; no full cutover follows from this adapter.

## T018 remaining writer composition

The existing acknowledge and saved-selection HTTP request shapes remain unchanged. `AcknowledgeIssuesAtomically` now receives explicit non-authoritative `IssueChangeAttribution`, locks every requested row in ID order, validates that the complete set still exists and is open, and runs the shared locked material/comment committer for each row plus the existing audit in one transaction. Its locked open-to-acknowledged condition owns the current revision; it is not a replacement for a caller's stale edit base. The unused unconditional `AcknowledgeIssues` entry has no runtime producer and is removed; session-start retains its bounded read-only summary and gains no new acknowledgment producer.

Saved selection still validates its original browser/session/selection-version binding at the existing handler. The store locks all original targets, rechecks authority and compares each bound microsecond timestamp before bridging that matched locked row to its material revision. It never refreshes a stale selection. `IssueSelectionOperation.Attribution` carries source/agent/session labels separately from authority; existing direct status-action author labels remain compatible attribution only. All selected mutations and optional comments, one field-name-only history per actual material revision, and the existing audit commit or roll back together. A normalized no-op writes no issue revision, timestamp or history. Delete retains the existing operator-only action checks, comment deletion, append-only retained history and immutable receipt tombstone; no new delete permission or retained payload snapshot is added.

`auth.Identity.IssueActor` owns the same accepted credential/browser/operator projection previously held in the issue application. `auth.IdentityKey` aliases the leaf issue contract's context key, allowing both the application and IssueStore to sample that existing immutable authenticated value exactly once without an auth→GORM→auth import cycle, a second identity policy, a new context allocation or an actor inferred from source_agent. Current HTTP/native composition and directly authenticated internal selection calls therefore use the same actor namespace and descriptor. Retained low-level legacy create/comment/lifecycle methods have only fixture/test consumers in the traced repository; they are not reactivated by any runtime adapter.

This is a bounded D1 cutover within the existing issue/auth/store owners, not a new subsystem or UI schema. Focused proof uses the accepted real HTTP/store T017 oracle for actor/history/no-op, stale original selection, real row-lock contention, persistence/audit rollback and delete non-resurrection, together with existing selection/store/auth and shared/native/HTTP regressions. Root owns integration and independent acceptance; T019/T020 consumer/conservation acceptance is not implied by a child GREEN.
